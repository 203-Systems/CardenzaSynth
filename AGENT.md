# CardenzaSynth Agent Notes

## CardenzaHAL: changed upstream, consumed here

`Devices/Cardenza/cardenza` is the git submodule https://github.com/203-Systems/CardenzaHAL, the shared Cardenza hardware layer: every firmware (this one, Cardenza-MPE, ...) builds on it instead of carrying drivers of its own.

- **Changes go upstream.** Since 2026-11-02 (user decision) we maintain it: work in a separate clone `~/projects/CardenzaHAL`, push to upstream `main`, then `make hal-update` here and commit only the new submodule pointer. Changes there reach every consumer: keep them generic and compatible, and say what changed.
- **The submodule is a consumer copy.** Never edit, commit or push inside `Devices/Cardenza/cardenza`; never pin it to a commit that is not on upstream `main`. `make HAL_DEV=~/projects/CardenzaHAL DEVICE=Cardenza build` builds against the clone instead, to test a HAL change before it is pushed; such a build may go on the test board but is never shipped (no Launcher bin for users).
- **Reuse it.** Use what the HAL provides through its public headers, included from the HAL root (`"cardenzaHAL.h"`, `"keyboard/keyboard.h"`, `"audio/audio.h"`, `"mic/mic.h"`, `"usb/usb.h"`): keyboard scan and key LEDs (`setLED`, `setLEDGlobalBrightness`, `enableLED`), audio TX with mono / stereo `Init` and codec volume, mic RX channel, display panel handles and backlight, SD card mount, Func button, IR, USB (MIDI, audio, HID, update commands). Do not re-implement a driver or a HAL feature in this repository.
- **Missing or wrong in the HAL?** Fix it in the HAL clone. `Devices/Cardenza` (the device layer, ours) is for what is specific to this firmware; `Devices/LedLight.h` models the LED scan for the simulators.
- **Enforced.** `make hal-check` runs before every firmware build and the CMake configure checks too: they fail when the submodule has local changes or a commit that is not on upstream, and they set the submodule's push URL to `no-push://…` (the clone is where pushes come from).
- The HAL keeps its own rules in its `AGENT.md` (ESP-IDF only, native handles, no copyleft code); follow them when changing it.

## Workflow

- Do not start builds from the agent unless the user explicitly asks for one.
- Prefer static validation such as `get_errors`, targeted searches, and diff inspection when editing the Cardenza HAL layer.

## Storage Rules

The spec is `docs/app-storage-protocol.md`; keep it in sync with behaviour changes.

- Apps store data only through the OS storage API (`OS/Storage`: `os::storage::AppFolder`, `AppSettings`, `SharedSamplesDirectory`, `WriteFileAtomic`), in their own app folder `Cardenza/Apps/<Author>/<Name>/` (plus `Shared/` for samples). Never hard-code card paths and never call `Device::Storage` from app code (enforced by ValidateArchitecture).
- `Device::Storage` is the low-level card (root, mount, free space, internal-flash records). Folder knowledge belongs to `OS/Storage`, not to the device layer.
- Settings are `key=value` text read tolerantly (unknown keys kept); change them in RAM and let the system write them (one second after the last change, on suspend). Volume, key LEDs and screen are device settings (`os::storage::Set…`); projects never carry them. The keyboard, chords and arpeggiators are project data, not settings.
- An app persists its working state in `Suspend()` (its `Session/` folder) and restores it in `Setup()`; the system destroys the app before it creates the next one. The groovebox also keeps it in internal flash during use, card or no card (`SessionStore`: small binary NVS records, only the ones that changed, written when nothing is heard) because users may pull the power at any moment. New project data must be added to `CaptureProject` and to the records in `SessionStore`, and every way to change a project must go through a key event (that is what starts a write). Do not change the partition table: it has to stay compatible with the Launcher.
- Groovebox project files are format 7 (format 6 made the play settings project data: keyboard, per-track chord and arpeggiator; format 7 gives every pattern its own length, up to 256 steps); version 5 was an unreleased development format with a PLAY line; the next format change takes version 8.
- The 0.1.0 release kept its files in `<card>/CardenzaSynth/{Projects,Samples,...}`. Nothing there moves or is written; `ListProjects` / `ResolveProjectPath` and `ListSamples` / `ResolveSamplePath` read it next to our own folders, ours first, so read projects and samples through those. Saving goes to our own folders only.
- Sample recordings are written straight to `Session/take-<track>.wav`, synced about once a second, and come back at the next start until saved or discarded. Samples longer than `sampler::kMaxRamSampleFrames` play from their file through `audio::SampleStream`; rename, replace or delete a sample file only under an `audio::SampleFileGuard` (FAT refuses that for an open file).

## Memory

The board has no PSRAM, so everything of a size is allocated when it is used and given back when it is not: steps of a pattern by page (`SynthSequencer::StepStore`, copy-on-write, a snapshot shares pages), the sample cache, the microphone ring (only while recording), delay and reverb lines. Never add large static buffers. With `-fno-exceptions` a failed plain `new` aborts the device: use `new (std::nothrow)` for anything large and report the failure on screen. libstdc++'s nothrow `new` calls plain `new` and aborts as well, so `Devices/Cardenza/Device.cpp` replaces it, and refuses a nothrow block of 4 KB or more that would leave less than 20 KB free: the small plain allocations need that room. Small nothrow blocks have no floor there (libraries such as NVS use them); optional small pieces of ours check for themselves (pattern pages stop at 24 KB, `kPatternHeapFloorBytes`; the effects' choruses and buses at 20 KB, `FxRoom`). Nothing per audio block may allocate. Host builds cannot show any of this: test running out of memory on the board.
An engine is hundreds of plain allocations: build one only through `GrooveApp::BuildEngine` (it checks the room with the size of that kind, learnt from what the heap gets back when one is destroyed, `DropEngine`; how much the heap shrinks while one is built counts other tasks too), never several beside the ones playing (`ReplaceSession` checks a whole project first, then swaps one track at a time; four new engines beside four old rebooted the board on loading a 0.1.0 project). Keep an engine's blocks small: its parameters are a deque (a DX7's list in one block is 9.5 KB, which a fragmented heap does not have); a new engine states its count with `ReserveParameters(count)`; preset values are stored compactly (`PresetValue`). The effects give their memory back while a project is built (`synth::audio::SuspendEffects` / `ResumeEffects`, which allocates before it returns), and a load or NEW that does not fit first parks the current patterns in the autosave (`GrooveApp::MakeRoom`, `RestoreSessionPatterns` when it still fails). `GrooveApp::UseHeapProbe` lets host tests run out of memory on purpose.

## Log

- Everything the firmware prints is the log: the device keeps it in an RTC ring that survives a crash (with the crash's `!!!` lines and backtrace, `Devices/Cardenza/DeviceLog.cpp`), and `OS/System/Log` appends it to `Cardenza/Logs/log.txt` while SETUP > SYSTEM > LOG (`sys.log`, on by default) is on. Users send that file; read it before guessing.
- Print a line where something happens that would explain a problem (a load, a save, a refusal, a failure: `Groove: …`, `ui: …`), never per audio block or per frame. Keep the writer cheap: no task, no heap buffer, bounded appends.
- Keep the ELF of every bin given to anyone: the backtrace is decoded with it (`xtensa-esp32s3-elf-addr2line -pfiaC -e CardenzaSynthFirmware.elf <addresses>`); the log's first line of every start names the version and ELF hash.

## Sound Rules

The numbers and the reasoning are in `docs/groovebox-design.md` (音频 and 混音).

- All three render paths end in `WriteOutputNoLock`: the line input (a computer playing over USB, `SetLineInput`) joins at unity, then `kOutputGain`, then the limiter. Never clip or saturate anywhere after the mix, and keep levels equal between the paths.
- `PresetLevels.inc` evens out the factory presets; regenerate it when a patch, the Juno mapping or a gain changes (the command is in the design doc). `kJuno` is ours and may differ from AMY's ROM: `VoiceJunoPatchNoLock` sends it over the ROM string.
- Voices render on two cores (`RenderAmyVoicesNoLock`) and the instruction cache is 32 KB because of it. A voice stays whole in one part (`VoiceSplitNoLock`): its first oscillator holds the filter and the envelope and renders the others, which sound raw when anything renders them on their own. Host builds have one core but render the same two parts, the second first, so tests hear it. The sequencer clock is a separate task on absolute time: nothing in rendering may hold it up. Overload sheds whole voices (`RenderLoad`, from how long renders take; `Groove: too much to render` in the log); it must never slow the clock or run the queue dry.
- Every note someone starts needs an owner that ends it, known to `GrooveApp::EndOrphanNotes` (`AddHeldPadNotes`, `AddSoundingNotes`, `Previewing`, `computerNotes_` for USB MIDI): that safety net silences notes nobody owns and logs it, so a new source of notes must be added there. Never send AMY note 0 (`SendAmyNoteEventNoLock`). `TestNoStuckNotes` fails when the net has to act.
- Check audio load on the board, not on the host: flash timing decides it. `audio timing` in the log gives avg / max per 1024 blocks; 1024 blocks must take 5.94 s, more means the queue ran dry.

## Groovebox UI Rules

The spec is `docs/groovebox-design.md`; keep it in sync with behaviour changes.

- Fixed key roles: left column ESC / TAB / FN / CTRL (icons on the screen's left edge, in the key's color, no labels and no state marks: where you are is in the header and the page tabs), right column ADD / SUB / ENTER / PLAY (ADD and SUB's icons follow `Controller::AdjustKeysMean`: up / down for a value and for a list alike, ADD, the upper key, raising the value and going up the list; sideways and erase have their own; a new screen says which it is there), columns 1–8 always play the current track, columns 9–12 mirror the on-screen 4x4 cell grid.
- Four scenes in two kinds, numbered as on screen: 0 SETUP comes first (the project and files, plus settings for every track and the device: KEYS, SYSTEM), outside the ring, reached only with ESC + GRID column 1 (or the FN menu); ESC there goes back to the scene it came from. 1 INSTR (the current track's sound, with its own CHORD and ARP pages), 2 SEQ (what it plays) and 3 TAPE (all tracks together: session, song, mix, sends, master FX) form the ring a tap on ESC walks. The device boots on INSTR VOICE, every project on T1 (`kDefaultActiveTrack`, the drum machine). New music pages go in scenes 1–3 by what they act on (one track's sound / one track's notes / all tracks); new global or device settings go in SETUP. INSTR pages run in signal order: VOICE, CHORD, ARP (not on drums), engine pages, FX.
- Holding a left key turns the GRID into a map of what that key switches (ESC scenes by column, TAB tracks laid out like MIX, CTRL every page of the scene, FN the menu of the current screen); choices go on the GRID, not on the pads or number keys. Keep each scene at 16 pages or fewer so the CTRL map fits.
- Colors carry meaning: ESC red-orange = scenes / back, TAB cyan = tracks, FN yellow = second functions, CTRL violet = pages, green = playing, red = recording / danger. Selection is terminal inverse (ink background, black text). Area fills use the 4x4 Bayer dither, not flat blocks.
- Nothing on the first level types: anything that needs a name (save as, rename) goes in the FN menu, the plain action picks a free name by itself (`FreePresetName`, `FreeTakeName`, `SONG nn`).
- A track with the drum engine has the drum machine as its note page (`Controller::DrumLayout()`, `DrawDrumMachine`): pads choose the lane and how hard, the GRID is that lane's steps, a tap adds at once, a tap on a hit removes it on release, hold + ADD / SUB is velocity, or the microstep after ENTER (`UiState::drumEditsMicrostep`). There is no ROLL / STEP there.
- Long lists are not kept in memory: a `Modal` holds the rows on screen (`firstItem`, `itemCount`, `Row()`), the preset browser asks the engine for them, and the Animator's snapshot copies only those. A list of 128 names is a contiguous block the device may not have, and a failed plain allocation reboots it.
- Holding a parameter's GRID cell turns the pads into its values (`Controller::CellParameter`, `CellPickerActive`): a new page with parameter cells adds them to `CellParameter` and `SetCellParameter`. A cell's own press action on a focused switch or choice runs on release (`CellPress::stepOnRelease`), so holding it never changes the value first.
- A pattern is 1–256 steps, shown one page (16 steps, `SequencerUiState::firstViewStep`) at a time: sequencer step numbers are absolute, `steps[]` is the page on the GRID. FN + ADD / SUB and the SEQ menu flip pages and set the length; the view follows the playhead until flipped by hand.
- The microphone takes the speaker's clock pin (GPIO43), so the device layer hands it over (`PauseOutputForInput` / `ResumeOutputAfterInput`) and the controller cancels a recording when its screen is gone.
- FN is the menu of the current screen (`Controller::Menu()`, `RunMenu`): held FN shows it on the GRID (FN + GRID runs an item), a tap keeps it open (`ModalKind::Menu`, GRID runs and closes). Rows 0–2 are the page's actions, row 3 is the same everywhere (SAVE, TAP, REC, SETUP / BACK). A new action for a screen goes into its menu (with its FN letter, if any); settings do not go in the menu, they go on a SETUP page. FN + CTRL is the previous page, FN + ADD / SUB big steps. In input screens (`FnYellowMode()`) FN is the yellow keycap layer instead (`; . , /` arrows, text cursor).
- Every Fn letter shortcut must be the `key` of a menu item, and every other Fn combination on the edge keys must appear in `Controller::FnEntries()` so the menu footer documents it.
- The left column is filtered in the device layer (`Devices/KeySettle.h`): a state must settle for 12 ms, and a key reading as held for over 15 s counts as released until it lets go. The filter logs what it did, which is how to tell a bad signal from a bug.
- Key LEDs are driven by CardenzaHAL (see the top of this file); it drives each key at 16 linear duties and gamma-corrects only the master level, so `Device::LED` key levels are perceived brightness and the device layer gamma-maps them (gamma 2.6, `Devices/LedLight.h`, also the simulators' model). Every key is off (`groove::kLedOff`, nothing there), half (`kLedHalf` = 6, the dimmest glow, HAL duty 1/15, there but not chosen) or full (`kLedFull` = 15, chosen / held / sounding / playing); Blink is the only effect (waiting; the Learn guide's hints blink at half its speed, `LedEffect::Hint`). Do not add in-between levels, breathing or press ripples, and never let an animation keep a key lit that the state says is off. The one exception, asked for by the user: the pads of a drum track, where a column is a drum and its rows are velocities (`kDrumRowVelocity`): they rest on a gradient and a hit runs along the column (`Animator::DrumWave`). That spread is for the key lights only: on screen the pads keep their blocks and show how hard by dither density. The screen's edge strips mirror the edge-key LEDs through `Animator::LedShown`.
- While FN is held no key may do its plain function: a key either has an FN function or does nothing (and its LED is off). Every FN shortcut and menu item reports its result with `Controller::ShowHud` (name, value, bar) or a toast.
- Settings that apply to every track (keyboard layout, scale, system) live on the SETUP settings pages (`SettingsPage`, `UiState::settingsFocus`) as `keys.*` / `proj.*` / `sys.*` slots. Each track's MIDI effects are its own: the chord (`UiState::chords`, `chord.*` slots) and the arpeggiator (one per track in `SynthSequencer`, `arp.*` slots) act on the current track and sit on its INSTR pages. All are handled by `SettingValue` / `AdjustSetting`.
- The Learn site opens on the guide (`docs/learn/guide.json`, `tools/learn/guide.py`, `guide.js`, `guide-anim.js`): short lessons, few words, pictures and the live device (the simulator, or a Cardenza on USB through the guide link, docs/groovebox-design.md 教程模式); the manual is its reference (`reference.html`). Every device lesson step has `keys`, `done` and `demo`; `make learn` runs the demos on the firmware and fails when a step does not complete, so a behaviour change that breaks a lesson shows there. A new state the lessons check goes into `Controller::GuideState` and the design doc.
- The Learn manual (`docs/learn`, built by `make learn` into `build/web/site/learn`, deployed with the web simulator) is an internal preview until release: do not update it with behaviour changes, only when asked. When it is updated it documents every key, page and setting in Chinese and English (same section ids; `<!-- keywords -->` and `docs/learn/synonyms.json` keep it searchable). Reference tables and screenshots are generated from the code (`tools/learn/learn_dump.cpp`, the shot script in `tools/learn/build.py`); the build fails on broken links, unknown screenshots or search regressions (`tools/learn/search.test.js`). Pictures follow the product's look (`tools/learn/figures.py`): highlights with numbered markers and a numbered legend (`mark` / `key` lines), key caps as the web simulator draws them, step strips (`{{strip`); no hand-drawn rings or arrows.
- Tracks are identified by color everywhere (`theme::TrackColor`); never color a specific track with a role color.
- Track effects are `fx.*` engine parameters registered by `PagedSynthEngine::RegisterTrackFxParameters()`; the master bus is `Host::MasterFx` (project data). Both are defined in `Library/Synth/Audio/SynthFx.h`.
- Danger (overwrite, delete, discard) always confirms with ENTER = yes, ESC = no.
- The UI must not include ESP-IDF headers or device HAL code (enforced by ValidateArchitecture); use `groove::Host`.
- Check visual changes with `CardenzaSimShot` screenshots before flashing.
